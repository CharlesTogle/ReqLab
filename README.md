# ReqLab — HTTP Request Inspector

**An HTTP request inspector built by a developer trying to fall in love with coding again.**

## Why This Project Exists

I've been coding for years, building applications, solving problems, and enjoying the process of turning ideas into working software.

Then AI changed how I worked.

I started spending more time writing prompts, managing agents, reviewing generated code, and fixing things I didn't write myself.

I was shipping faster, but I wasn't enjoying it as much.

Somewhere along the way, I realized I missed actually coding.

I missed staring at a problem, figuring out how things worked, making mistakes, debugging for hours, and finally getting something to work because **I understood it.**

Agentic coding is powerful, and I believe it's part of the future of software engineering. But constantly delegating the thinking made me feel disconnected from the craft I originally fell in love with.

So I'm building ReqLab.

Not because the world needs another Postman alternative.

Not because I'm trying to launch a startup.

Not because I want to add another impressive project to my portfolio.

**I'm building this because I want to write code again.**

## What Is ReqLab?

ReqLab is a lightweight HTTP request inspector built with Next.js.

It allows developers to construct HTTP requests, send them to APIs, and inspect responses.

Think of it as a minimal Postman alternative, built from scratch as a way to explore HTTP, browser APIs, networking, and software engineering fundamentals.

### Planned Features

- [ ] HTTP requests (GET, POST, PUT, PATCH, DELETE)
- [ ] Custom request headers and query parameters
- [ ] JSON and text request bodies
- [ ] Response status, headers, and body inspection
- [ ] Request timing and response size measurements
- [ ] JSON formatting
- [ ] Request cancellation and timeout handling
- [ ] Local request history
- [ ] Saved request collections
- [ ] Response comparison
- [ ] Optional server-side request proxy

## Tech Stack

- **Next.js** — Framework
- **TypeScript** — Language
- **Tailwind CSS** — Styling
- **shadcn/ui** — UI Components
- **Fetch API** — HTTP Requests
- **IndexedDB** — Local Persistence

No unnecessary infrastructure. No complicated architecture. Just building things and understanding how they work.

## The Rules

This project has a few personal rules:

**1. No AI-generated implementations.**

I write the code myself. AI can help explain concepts, discuss approaches, or review my work, but it doesn't get to build the project for me.

**2. Understand before implementing.**

No blindly copying code. If I use something, I should understand why it works.

**3. No pressure to ship.**

There are no deadlines, clients, or expectations. This project can take as long as it needs.

**4. Keep things simple.**

No premature abstractions, unnecessary dependencies, or overengineering.

**5. Enjoy the process.**

Getting stuck is fine. Making mistakes is fine. Spending an entire afternoon figuring out one bug is fine.

That's part of programming.

## What I Hope to Learn

I want to revisit the fundamentals that sometimes get hidden behind frameworks, libraries, and AI-generated abstractions:

- How HTTP requests and responses actually work
- How to handle asynchronous operations properly
- How browser APIs behave and where their limitations are
- How to design maintainable application state
- How to approach errors, edge cases, and debugging
- How to solve engineering problems independently

More importantly, I want to rebuild the confidence that comes from knowing I can figure things out myself.

## A Note on AI

This isn't an anti-AI project.

AI is an incredible tool, and I don't intend to stop using it professionally.

But there's a difference between using AI to become a better engineer and becoming so dependent on it that you stop exercising your own problem-solving skills.

I'm trying to find that balance again.

I don't need to be the fastest developer.

I don't need to automate every part of my workflow.

Sometimes, I just want to open VS Code, put on some music, and write code.

## Final Thoughts

Maybe this project becomes a useful developer tool.

Maybe it stays unfinished.

Maybe nobody else ever uses it.

That's okay.

For once, the goal isn't productivity, performance, or shipping something impressive.

**The goal is to enjoy programming again.**
